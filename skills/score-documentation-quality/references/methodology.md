# Методология оценки и последовательного улучшения документации

## Назначение

Оценивать, насколько конкретной версии документации можно доверять при принятии решений и выполнении действий. Не измерять количество текста и не подменять проверку фактов структурными метриками.

Оценивать один связный документный контур с одной целью: отдельный документ либо набор authority/core/supporting-файлов, совместно обслуживающих одну задачу. Не усреднять несвязанные документы и не повышать балл добавлением безопасного вспомогательного текста. Для разных целей или профилей создавать отдельные оценки.

## Выбрать глубину

- Для явно заданной правки без неоднозначного owner/precedence использовать быстрый режим из `SKILL.md`; этот режим не требует manifest, графа, line transactions или 32-критериальной оценки.
- Для запроса на score, аудит или quality gate применять разделы оценки этой методологии, но не выполнять миграцию инструкций без отдельного запроса.
- Раздел последовательной нормализации применять только после deep-gate: явного deep/graph/adversarial запроса либо доказанного owner conflict, routing cycle, неоднозначного contract DAG или decision-changing precedence conflict.
- Не повышать режим только из-за количества файлов, переименования или переноса корневых инструкций.

## Зафиксировать область

Если пользователь не перечислил полный контур, сначала выполнить bounded discovery. Перечислить относительные пути Markdown-файлов внутри разрешённого репозитория; для поиска кандидатов прочитать только имена, frontmatter, H1/H2 и явные role/owner-метаданные. Затем прочитать routing-разделы применимого `AGENTS.md` и единственного кандидата, который по роли владеет правилами оформления/ведения документации, и извлечь пути ссылок, не открывая их цели. Не считать owner отсутствующим только из-за битого routing: вывод 0/1/несколько кандидатов допустим лишь после этого bounded inventory. Несколько кандидатов означают owner conflict. Discovery не является смысловой оценкой.

До выставления баллов записать:

- цель оценки;
- точную версию, commit, дату снимка или иной неизменный идентификатор;
- все единицы оценки с ролью `authority`, `core` или `supporting`, SHA-256 содержимого и общим scope digest;
- профиль каждой единицы: `instruction`, `runbook`, `specification`, `guide` или `reference`;
- намеренно исключённые источники.

Числовую оценку выдавать только после чтения всех единиц зафиксированной области. Недоступный внешний источник не делает область неполной: отметить зависимый критерий `unknown` и привести evidence вида `unavailable`. Если один набор обслуживает несколько независимых целей, разделить его до оценки.

## Последовательно нормализовать иерархию инструкций

Применять этот раздел только в режиме глубокой миграции. Для быстрой правки следовать `SKILL.md`; для read-only оценки читать все единицы зафиксированной области без изменений.

### Канонизировать topology и имена

Обрабатывать верхнеуровневые инструкции только в такой очереди:

1. корневой применимый `AGENTS.md`;
2. корневой `DOCS.md`;
3. корневой `MODEL.md`;
4. корневой `WORKFLOW.md`;
5. нижестоящие контракты — строго по одному.

Определять файлы по роли, а не по исходному имени. `DOCS.md` владеет правилами оформления, размещения, именования и lifecycle документации; `MODEL.md` — project-specific model behavior; `WORKFLOW.md` — порядком действий, gates, переходами состояний, recovery и escalation; contracts — только узкими явно routed доменами. Если применимый корневой `AGENTS.md` отсутствует, создать минимальный файл с invariants и маршрутом к `DOCS.md`; несколько применимых owners являются blocker.

До применения результата inventory зафиксировать immutable baseline manifest/hashes и declared migration plan со всеми ожидаемыми creations, renames, путями archive и его `.head.json`. Первый pre-destructive `add` одновременно инициализирует archive; чистое создание нового файла ничего не удаляет и отдельного `init` не требует. Для `DOCS.md` обработать 0/1/несколько: при одном кандидате сначала byte-exact архивировать весь старый файл и выполнить `verify`, затем перенести его в корень как `DOCS.md` и обновить входящие ссылки/graph evidence; при нескольких либо при содержательно разных `DOCS.md` и аналоге запросить решение; при нуле создать минимальный `DOCS.md`. Выполнить это до смыслового подключения `MODEL.md` и `WORKFLOW.md`.

Для `MODEL.md` и `WORKFLOW.md` применять ту же развилку только после `AGENTS.md` и `DOCS.md` в состоянии `plan_stable`: одного role-equivalent кандидата архивировать целиком и канонизировать, при нуле создать минимальный canonical файл на соответствующем этапе, при нескольких остановить зависимую ветвь. Не создавать их заранее и не выбирать по похожему имени без подтверждения роли.

В `DOCS.md` закрепить:

- верхнеуровневые инструкции находятся в корне и соответствуют `^[A-Z][A-Z0-9_-]*\.md$`;
- обязательные canonical names: `AGENTS.md`, `DOCS.md`, `MODEL.md`, `WORKFLOW.md`;
- контракты находятся в `contracts/` и соответствуют `^[a-z][a-z0-9-]*\.md$`;
- `AGENTS.md` направляет к `DOCS.md`, а `DOCS.md` маршрутизирует к `MODEL.md`, `WORKFLOW.md` и их contracts;
- byte-exact append-only archive по умолчанию находится в `archive/instructions.jsonl`, его проверяемый head — в `archive/instructions.jsonl.head.json`; оба пути не являются authority, а записи хранят Base64/SHA-256 и образуют hash chain.

Baseline остаётся неизменным доказательством исходного состояния. После каждой заявленной мутации формировать новый stage manifest/hashes/scope digest; добавление заранее declared canonical/archive path не расширяет scope, незаявленный файл требует отдельного разрешения. Будущий контракт не может задним числом задавать policy верхнему уровню; такой случай является новым конфликтом.

### Упростить корневую пару

Разбирать `AGENTS.md`, затем `DOCS.md` сверху вниз. Единицей считать одно атомарное утверждение либо один supporting-блок, даже если Markdown переносит его на несколько физических строк. Это line transaction: до следующей единицы записать `content_kind = normative|supporting`, точный locator и одно действие, немедленно обновить ledger и graph delta, независимо подтвердить semantic edges и пройти локальный migration gate. Не накапливать несогласованный пакет строк.

| Действие | Условие |
|---|---|
| `keep` | Правило принадлежит роли файла, имеет владельца и не дублируется |
| `move` | Содержание нужно, но target ещё не подключён либо canonical owner находится ниже |
| `archive` | Содержание доказанно obsolete либо surviving copy уже validated, reachable, applicable и имеет confirmed owner |
| `rewrite` | Смысл нужен, но scope, modality, термин или ссылка неоднозначны |
| `decision` | Исправление требует выбора policy, authority, precedence или owner |

В `AGENTS.md` оставлять верхнеуровневые invariants, authority/precedence, обязательный основной маршрут и минимальные ссылки. Не превращать его в индекс всех контрактов: документационную ветвь подключать одной явной ссылкой на `DOCS.md`, если иной routing не доказан требованиями.

В `DOCS.md` оставлять архитектуру документации: canonical topology, типы и владельцев, placement/naming, lifecycle, archive и routing. Команды инструментов, доменные процедуры и повтор invariants переносить в canonical targets. Supporting-текст не удалять лишь потому, что он не decision-changing: сначала проверить его вклад во все 32 критерия, включая examples, assumptions, recovery, navigation, audience и accessibility.

Сначала довести root-файл до `plan_stable`: роли, target и действия определены, но каждый `move` остаётся действующим в source. До удаления, замены или переименования вызвать `scripts/archive_instruction_content.py add` для целого исходного файла либо точного byte-span. Запись в `archive/instructions.jsonl` хранит исходный path, locator, byte offsets, Base64, длину, content/record SHA-256, content kind, причину, target и status; записи образуют hash chain, а sidecar head обнаруживает усечение. `add` сериализует concurrent writers и возвращает byte-bound `evidence_*` для графа. До мутации обязательно выполнить `verify`; для выборочной проверки использовать `extract` в новый файл и сравнить байты. Даже duplicate и obsolete сначала архивировать. Файл становится `content_final` только после подключения всех targets, удаления source spans, обновления archive/ledger, hashes и повторной проверки parent-графа.

Пример обязательного pre-mutation gate:

```bash
python3 scripts/archive_instruction_content.py add --root SCOPE_ROOT \
  --source OLD_PATH --locator LOCATOR --content-kind mixed \
  --reason REASON --target TARGET [--start-byte N --end-byte M]
python3 scripts/archive_instruction_content.py verify --root SCOPE_ROOT
```

### Подключать верхний уровень и контракты

После plan-stable корневой пары построчно обработать `MODEL.md`, затем `WORKFLOW.md`, после них — ready contracts. Для каждого файла:

1. зафиксировать его назначение, parent, scope и место в очереди;
2. построчно сопоставлять normative и supporting content со стабилизированным верхним графом; каждую line transaction завершать candidate/manual delta, rehash/digest и migration gate до следующей;
3. разрешить дубли, терминологический drift и precedence до подключения;
4. для текущей строки создать model-assisted candidate delta, затем передать её span независимому clean-context reviewer для отдельного manual graph с node-level provenance;
5. добавить подтверждённые artifact/rule/entity-узлы и ownership/precedence/scope-рёбра и запустить `check_instruction_graph.py --migration-gate`; rule/entity без confirmed provenance блокируют переход;
6. добавить одну routing/trigger-строку в канонического parent;
7. независимо подтвердить canonical `routes_to`-ребро, обновить hashes и scope digest и повторить migration gate; обычное `references` не задаёт parent;
8. архивировать и удалить соответствующие pending source spans, затем повторно проверить изменённые parents;
9. отметить файл `connected/content_final` только после всех проверок.

При отсутствии independent reviewer разрешено только `deterministic_confirmed`, полученное реальным воспроизводимым parser/checker; не маркировать собственный вывод как `independent_agent`. Иначе ветвь остановить.

Для contracts построить dependency DAG из явных `references`/`derives_from` и declared prerequisites. Выбирать ready-узел; при равенстве — лексикографически по пути. При blocker остановить только узел и descendants и продолжить готовую независимую ветвь. Цикл требует решения пользователя. Каждый contract обязан иметь ровно один входящий confirmed `routes_to` от canonical parent; обычные cross-references не считаются parent. `routes_to` запрещает self-edge и циклы. Различия scope моделировать правилами/trigger, а не вторым parent. Не создавать routing на draft/placeholder или dangling dependency.

После последнего контракта выполнить `check_instruction_graph.py --final-topology-gate`, независимое clean-context review и один correction pass для blocker/high. После любой коррекции повторить затронутые migration gates и final topology gate. Только затем фиксировать финальные hashes и выполнять полную 100-балльную оценку.

Хранить рабочий ledger во временном каталоге: `source locator`, полный source span, content kind, действие, archive locator, target locator, graph IDs, gates и status. Ledger не заменяет долговечный archive и не является authority.

## Собрать доказательства

Каждое доказательство содержит `kind`, `path`, `locator` и `note`.

| `kind` | Значение |
|---|---|
| `supports` | Наблюдение подтверждает выполнение критерия |
| `gap` | Наблюдение показывает отсутствие или ограничение |
| `conflict` | Наблюдение является одной стороной противоречия |
| `unavailable` | Нужный источник назван, но недоступен в разрешённой области |

Использовать воспроизводимый локатор: строку, заголовок, JSON Pointer, якорь или точный идентификатор проверки. Доказательства из оцениваемых документов должны ссылаться на путь из `scope.units`. Доступный внешний первичный источник сначала сохранить как зафиксированную единицу scope; произвольный URL не является проверенным evidence. URL допустим только для `unavailable`.

Разделять:

- факт — наблюдаемое содержание или результат проверки;
- вывод — статус критерия, следующий из фактов;
- рекомендацию — предлагаемое изменение, не доказательство текущего состояния.

Статический сканер выдаёт только кандидатов для проверки. Не преобразовывать число заголовков, ссылок, строк или предупреждений в баллы.

## Оценить критерии

Рубрика содержит 32 фиксированных критерия общей стоимостью 100. Для каждого выбрать один статус:

| Статус | Балл | Обязательное evidence |
|---|---:|---|
| `met` | 100% стоимости | только `supports`, минимум один из authority/core, без нерешённого decision-changing пробела |
| `partial` | 50% стоимости | `supports` из authority/core и минимум один `gap` или `conflict`, без `unavailable` |
| `unmet` | 0% | только `gap` или `conflict` |
| `unknown` | диапазон 0–100% стоимости | только `unavailable` |

`partial` означает ограниченно работающее содержание, а не неуверенность ревьюера. Не использовать его для повышения удобного итогового балла. Для authority/core-файла decision-changing пробел не может быть компенсирован supporting-файлом. В evidence критерия хранить наблюдения, определяющие его статус; дополнительные недецизионные наблюдения описывать в rationale или limitations, не смешивая несовместимые статусы.

`review.schema.json` проверяет структуру. `calculate_score.py` дополнительно проверяет межполевые инварианты: digest, hashes, роли evidence, допустимые сочетания status/kind, уникальность первопричин и caps.

Баллы по измерению равны сумме его критериев. Подтверждённый итог использует нижнюю границу `unknown`, потенциальный — верхнюю. Точность результата — 0,5 балла.

## Учитывать профиль

Не менять смысл критериев и веса. Использовать профиль только для выбора ожидаемого evidence:

| Профиль | Ключевое evidence |
|---|---|
| `instruction` | scope, authority, precedence, обязательность, разрешённое и запрещённое поведение |
| `runbook` | предусловия, команды, состояние, проверка, откат, эскалация |
| `specification` | схемы, состояния, принятые, отклонённые и граничные случаи, ошибки |
| `guide` | выполнимый путь, ожидаемый результат, объяснение и устранение проблем |
| `reference` | полная сущность, стабильная навигация, версия и точные определения |

Не сравнивать численно документы разных профилей как взаимозаменяемые продукты. Допустимо сравнивать версии одного контура или одинаковые профили с одинаковой целью и областью.

## Применить системные ограничения

Системный finding не вычитает баллы. Он только ограничивает максимально допустимый итог, когда локальные сильные стороны могли бы скрыть блокирующий дефект.

| Тип | Максимум | Условие |
|---|---:|---|
| `critical_authority_conflict` | 39 | Два применимых authority требуют несовместимых действий без разрешённого приоритета |
| `operational_contradiction` | 59 | Основной сценарий требует несовместимых действий или результатов |
| `missing_core_authority` | 59 | Решение требует authority, которой нет в области или разрешённом первичном источнике |
| `broken_core_path` | 69 | Основной переход, команда, ссылка или пример не работает |
| `material_ambiguity` | 79 | Неоднозначность меняет решение или результат типового случая |
| `material_primary_source_mismatch` | 59 | Decision-changing утверждение прямо расходится с доступным первичным источником или проверенным поведением |

Для каждого finding задать стабильные `id` и `root_cause`. Не регистрировать одну первопричину под разными типами. Доказательства должны иметь уникальные сочетания `path + locator`; противоречие требует минимум двух различных локаторов. Выбрать одно самое узкое применимое ограничение на первопричину. Локальные дефекты отражать статусом критерия, а не отдельным системным finding.

Непроверенность первичного источника оставлять `unknown`. Применять `material_primary_source_mismatch` только после подтверждения двух сторон расхождения.

## Разрешить конфликт через пользователя

Оценка фиксирует конфликт, но не создаёт новую policy. Если устранение подтверждённого конфликта требует выбрать authority, precedence, owner, обязательное поведение или допустимый fallback, сначала представить пользователю:

- две или более конфликтующие стороны и точные локаторы;
- общую область применимости и первопричину;
- применимый порядок приоритета либо факт его отсутствия;
- два-три взаимоисключающих варианта решения;
- последствия каждого варианта: какое поведение изменится, какой источник станет canonical, что потеряет силу и какие риски останутся.

После объяснения запросить явный выбор. До ответа разрешено закончить score и read-only отчёт; запрещено выбирать вариант, редактировать зависимые документы или выдавать предложенную policy за принятую. Если действующий precedence уже однозначно выбирает правило, пользовательский выбор не нужен: отметить нижестоящее нарушение и предложить привести его в соответствие.

## Ограничить циклы ревью

Baseline и hashes исходной области фиксировать один раз. В быстрой правке выполнить один согласованный edit pass, один итоговый смысловой pass и повторять только затронутые проверки. В глубокой миграции выполнять line transaction и migration gate только для перемещаемых или конфликтующих decision units, затем провести независимое review лишь когда оно запрошено или является обязательным evidence. В read-only score-режиме ничего не исправлять и не строить граф без deep-gate. После завершения применимого режима выполнить не более одной полной оценки для каждой связной цели/профиля. Любая правка после расчёта меняет hashes и аннулирует соответствующий review.

Формула для обеих границ:

`итоговая граница = min(минимальный применимый cap, сумма критериев этой границы)`

## Определить уверенность

Калькулятор выводит уверенность автоматически по стоимости критериев `unknown`:

| Уровень | Условие |
|---|---|
| Высокая | `unknown = 0` |
| Средняя | `unknown` стоит не более 10 баллов |
| Низкая | `unknown` стоит более 10 баллов |

При высокой уверенности нижняя и верхняя границы совпадают. Иначе показывать диапазон `X–Y/100`; не скрывать его одной точкой. Release gate использует подтверждённую нижнюю границу, требует сверки scope hashes с файлами через `--root` и запрещён при низкой уверенности.

## Интерпретировать результат

| Балл | Уровень |
|---:|---|
| 90–100 | эталонная |
| 80–89,5 | надёжная |
| 70–79,5 | рабочая |
| 60–69,5 | ограниченно пригодная |
| 40–59,5 | рискованная |
| 0–39,5 | непригодная |

Если границы диапазона относятся к разным уровням, маркировать уровень как неопределённый и перечислять источники неизвестности. Не считать разницу меньше двух баллов значимой без одинаковой версии, области, цели и профиля.

## Сформировать отчёт

Отчёт обязан содержать:

- цель, версию, единицы, роли, профили и исключения;
- подтверждённый и потенциальный баллы;
- восемь измерений и все 32 статуса;
- evidence каждого критерия с локаторами;
- системные ограничения и их evidence;
- рассчитанную уверенность;
- от одной до пяти сильных сторон;
- от одной до пяти приоритетных улучшений;
- ограничения проверки и недоступные источники.

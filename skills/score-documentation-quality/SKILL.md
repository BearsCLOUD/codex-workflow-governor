# Оценивать и улучшать документацию

## Выбрать минимально достаточный режим

До чтения методологий выбрать самый дешёвый режим, способный изменить решение:

1. **Быстрая правка — по умолчанию.** Использовать, когда пользователь назвал файлы или итоговую структуру, владельцы и target понятны, а decision-changing конфликт не обнаружен.
2. **Формальная оценка.** Использовать, когда пользователь просит балл, read-only аудит, сравнение версий, публикационную готовность или quality gate.
3. **Глубокая миграция.** Использовать только по явному запросу на deep/formal/adversarial/graph-проверку либо при нескольких применимых owners, неизвестном precedence, цикле routing, неоднозначном contract DAG или конфликте, который нельзя разрешить прямым чтением.

- Начинать в быстром режиме и повышать глубину только при первом конкретном blocker.
- Не считать несколько файлов, переименование или перенос четырёх корневых инструкций основанием для глубокой миграции.
- Не создавать граф, ledger, manifest, JSON review, дополнительную ветку или независимое ревью, если результат не может изменить решение.
- Не использовать число файлов, строк, связей или предупреждений как самостоятельный повод усложнить режим.

## Соблюдать границы

- Начать с названных пользователем файлов и применимых `AGENTS.md`/`DOCS.md`; выполнять bounded discovery только когда owner или полный контур действительно неизвестен.
- До изменения зафиксировать цель, точные пути и фактическую исходную ревизию.
- При публикации сначала получить актуальный head целевой ветки; не готовить параллельную устаревшую версию.
- Не расширять область без разрешения.
- Работать read-only, если пользователь явно не попросил исправить документы.
- Создавать промежуточные отчёты только во временном каталоге вне проверяемого репозитория.
- Не считать объём, оформление или статический скан доказательством смысловой корректности.
- Не запускать субагентов в быстром режиме. В других режимах использовать их только по запросу либо когда независимость является обязательным evidence и не задерживает основной путь.

## Выполнить быструю правку

1. Прочитать каждый применимый файл один раз и выписать только owner, scope, routes, ограничения и удаляемые фрагменты.
2. До удаления, замены или переименования сохранить точную исходную версию файла либо фрагмента в существующем non-authoritative archive вне instruction-loading paths. Если такого пути нет, использовать `legacy/instructions/<date>/`. Исключение: не копировать в репозиторий credentials, токены, private keys, персональные данные или юридически ограниченный материал; при подозрении остановить зависимое удаление, запросить разрешённое защищённое хранилище и проверить Git history до публикации.
3. Сохранять фактическую версию целевой ветки, а не устаревшую локальную копию. Проверить точность hash/blob-сравнением либо полным покрытием удаляемых нормативных строк.
4. Не создавать JSONL/hash-chain archive, если пользователь или глубокий режим не требует byte-level восстановления отдельных spans.
5. Изменить документы одним согласованным проходом сверху вниз: `AGENTS.md → DOCS.md → MODEL.md → WORKFLOW.md → contracts`.
6. Не проводить отдельную transaction, hash и graph gate для каждой строки.
7. Выполнить только релевантные проверки: относительные ссылки, canonical имена и placement, один owner на правило, отсутствие decision-changing противоречий, заявленный лимит размера, `git diff --check` и статический сканер при наличии.
8. После correction повторить только затронутую проверку и выполнить один итоговый смысловой проход по изменённому контуру.
9. При разрешённой публикации создать один атомарный commit поверх актуального target head. Не создавать промежуточную ветку, если пользователь явно разрешил прямую запись в целевую ветку.

В быстром режиме не создавать `review.json`, 32-критериальную оценку, semantic graph, per-line ledger, stage manifests, migration gates или independent review.

## Выполнить формальную оценку

1. Прочитать [методологию](references/methodology.md) полностью.
2. Зафиксировать одну связную цель, версию, единицы, роли `authority|core|supporting`, профили и исключения.
3. Запустить `scripts/scan_documentation.py` для локальных Markdown-файлов и проверить findings вручную.
4. Прочитать все единицы области и составить реестр authority, утверждений, действий, исключений, недоступных источников и конфликтов.
5. Создать `review.json` только во временном каталоге через `calculate_score.py --template`.
6. Заполнить все 32 критерия evidence со статусами `met|partial|unmet|unknown`; применять cap только к одной блокирующей первопричине.
7. Рассчитать результат через `calculate_score.py REVIEW --root SCOPE_ROOT --format markdown` и повторно сверить hashes.
8. Для quality gate использовать `--fail-below N`.
9. Если пользователь одновременно просил исправление и score, сначала завершить правку, затем выполнить одну финальную оценку. Не пересчитывать все 32 критерия после каждой строки.

Не строить граф только потому, что профиль равен `instruction`. Для явной четырёхфайловой иерархии достаточно прямой owner/route/precedence-проверки.

## Выполнить глубокую миграцию

Только после срабатывания deep-gate полностью прочитать [методологию](references/methodology.md) и [методику графа](references/semantic-graph-methodology.md).

1. Зафиксировать immutable baseline и declared migration paths.
2. Использовать `archive_instruction_content.py` для byte-exact archive, когда требуется восстановление отдельных spans или проверяемая hash chain. Скрипт должен fail closed на распознаваемых secrets; чувствительный материал архивировать только вне репозитория в явно разрешённом защищённом контуре.
3. Сохранять порядок `AGENTS.md → DOCS.md → MODEL.md → WORKFLOW.md → contracts`.
4. Использовать line transactions, ledger и graph delta только для реально перемещаемых или конфликтующих decision units, а не для неизменяемого текста.
5. Строить semantic graph только когда есть несколько owners/scopes, precedence/override, aliases, contract DAG или подозрение на цикл/противоречие, которое не покрывает прямая таблица.
6. Не маркировать собственный вывод как `independent_agent`; inferred/model-assisted edges оставлять candidates до независимого или пользовательского adjudication.
7. Запускать `--migration-gate` и `--final-topology-gate` только для миграции topology/authority/contracts.
8. Выполнить одну финальную 100-балльную оценку только если пользователь запросил score или quality gate.

## Запрашивать решение при конфликтах

При подтверждённом decision-changing конфликте показать обе стороны с локаторами, scope и precedence, объяснить первопричину и предложить два-три взаимоисключающих решения с последствиями. Приостановить только зависимое изменение и запросить явный выбор.

Не спрашивать, если precedence однозначно разрешает конфликт. Не превращать молчание пользователя в согласие.

## Представить результат

Для быстрой правки сообщить только изменённые файлы, сохранённый архив, выполненные проверки, target/commit и оставшийся blocker. Не выводить внутренние manifests или графовые метрики.

Для формальной оценки начать с `Итог: X/100` либо `Итог: X–Y/100`, затем указать уровень и уверенность. Показать область, восемь измерений, системные ограничения, сильные стороны, приоритетные улучшения и ограничения проверки. Полный evidence дать в ответе либо во временном JSON по запросу.
